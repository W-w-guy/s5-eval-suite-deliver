# S5-EVAL-012 招商 AI 评测集 biz_ai.resource_match

## 一句话
35 条资源匹配评测用例（常规 20 / opt_out 或利益冲突陷阱 9 / 无合适资源 6），
每条 context 含 8–15 个虚构候选资源，配 recall@3、MRR 与推荐理由有据率三项计算脚本。

## 目录
```
data/cases.jsonl        35 条用例（need / gold_resources / forbidden_points / expect_no_match）
contexts/*.json         每条用例的候选资源池（8–15 个）
match_eval/metrics.py   recall@K / MRR / 理由有据率
match_eval/__main__.py  runner（打分排除 -> 排序 -> 写理由 -> 指标 -> 报告）
tools/gen_cases.py      用例与资源池生成器（同源，gold 可取证）
suite_2008.yaml         套件定义
tests/                  26 个 pytest（含 recall/MRR 手算用例）
verify_2008.py          4 条 AC 的 24 项断言
```

## 怎么跑
```bash
python -m match_eval                                   # 全达标 rc=0
python -m match_eval --break-optout --tag bad          # 忽略 opt_out/冲突 -> 触发 forbidden
python -m match_eval --break-reason --tag bad2         # 理由编造字段值 -> 有据率掉 0
python -m pytest tests -q                              # 26 项
python verify_2008.py                                  # 24 项 AC 断言
```

## 五件必须先说清的事

**1. 陷阱资源必须「表面高度匹配」才叫陷阱。**
9 条陷阱里的被排除资源，行业与服务类型都与需求完全吻合，只是 `opt_out=true`
或与需求方存在 `conflict_with`。只有真读了这两个字段才不会推错。
验证脚本断言了这一点（否则陷阱不成其为陷阱）。

**2. 核心匹配（行业+服务类型）必须是必要条件。**
初版只按加权总分排序，一个行业与服务类型都不对、只是站点相同的资源仍能拿 1.0 分 > 0，
于是「无合适资源」用例**6/6 全部没输出「暂无合适匹配」**。加上必要条件后 6/6 正确。

**3. MRR 的 K 与 recall 的 K 不是一回事 —— 我自己手算错过一次。**
`gold=[A], ranked=[B,C,D,A]`：recall@3 = 0（第 4 名不进前 3），但 **MRR = 1/4 = 0.25**
（MRR 不看 K）。我最初把 MRR 也写成 0.0，实现是对的、手算错了。已在 verify 注释里记下。

**4. 理由有据率是「逐字段回查」，不是「看着像对」。**
理由里形如 `行业：X` 的引用会被抽出来，与候选资源真实字段比对，不一致记为无据。
`--break-reason` 让 mock 编造字段值，实测有据率掉到 **0.0000** —— 证明这一项真的在检查内容。

**5. 无合适资源用例的资源池经过反向改造。**
生成后把所有资源的行业与服务类型都改成与需求不同的值，确保「按当前判据它凭什么是空的」
成立。测试里逐条断言 `core_match == 0`。

## 已知局限（如实写）
- 被测工具是 echo mock（规则打分 + 模板理由），不是真实模型；它证明的是判定链路有效。
- 真实模型的理由往往是自由文本，字段值可能以同义表述出现（如「环保行业」而非「节能环保工程」），
  当前 `grounded()` 只认原样匹配，会偏严。接真实模型时建议加同义词表或交人工抽检。
- 35 条只够验证链路与门槛，不够估置信区间。
